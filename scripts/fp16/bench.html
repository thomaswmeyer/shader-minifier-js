Does mediump actually run faster here?

A minifier can drop a shader from highp to mediump, which is fp16 on most phone GPUs and fp32 on most desktop ones. That trade is only worth its accuracy risk if the hardware in your hand really is quicker at the narrower type. This page times both on it.

Rounds alternate highp, mediump, highp… so that a phone heating up under the load shifts both columns together. A drift down the row is throttling; the medians are what the verdict uses.

How it measures

  • Two programs per workload, byte-identical but for the precision line, each an unrolled 64-iteration dependent chain seeded from gl_FragCoord and a uniform, so nothing folds away at compile time.
  • Each pass renders a full-screen triangle into an offscreen RGBA8 target several times, then reads one pixel back — the read is what forces the driver to finish the work inside the window being timed.
  • Timing is performance.now() around that block. EXT_disjoint_timer_query would be cleaner but almost no mobile browser exposes it; the device strip says whether yours does.
  • A ratio near 1.00 means the two precisions cost the same here. That is the normal answer on desktop GPUs, which have no fp16 path, and it is also what you get when a workload is bound by something other than ALU throughput.
  • Speed is only half the question. Whether a given shader still looks right in fp16 is what the minifier's half-precision emulation checks offline, shader by shader.
