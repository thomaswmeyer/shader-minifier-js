Does mediump actually run faster here?

A minifier can drop a shader from highp to mediump, which is fp16 on most phone GPUs and fp32 on most desktop ones. That trade is only worth its accuracy risk if the hardware in your hand really is quicker at the narrower type. This page times both on it, and times highp against itself to show you how much of any difference is just noise.

The declared column is what getShaderPrecisionFormat promises, and it is nearly useless: 10 bits for mediump is both the fp16 figure and the floor the spec demands of everyone, so a driver that computes in fp32 anyway reports exactly the same thing. The measured column asks the GPU instead — it finds the smallest 2−k that a declared-precision add can still tell apart from 1.0, which is the mantissa width actually being used. A narrow answer is proof of fp16. A wide one means nothing in that path narrowed the value, which is either genuine fp32 hardware or a shader translator that ignored the qualifier.

How it measures

  • Two programs per workload, byte-identical but for the precision line, each an unrolled 64-iteration dependent chain seeded from gl_FragCoord and a uniform, so nothing folds away at compile time.
  • Every program is compiled and run several times before any timing starts, because drivers finish specialising a shader on its first real draw.
  • A pass is one draw of a full-screen triangle into an offscreen target, its loop count set by a uniform so the pass takes about 60ms, followed by reading one pixel back — the read is what forces the driver to finish inside the timed window. Both precisions of a workload always run the identical number of iterations. Scaling the work by drawing repeatedly instead does not survive a tile-based GPU: with no blend and no depth each triangle completely covers the last, and a deferred renderer shades only the final one.
  • Before timing anything, the page checks that doubling a pass's iteration count doubles its time. If it does not, the work is being discarded or the clock is too coarse to see it, and the page says so instead of printing a ratio.
  • The number reported is the fastest pass, not the average. Anything else sharing the GPU can only make a pass slower, so across many rounds the minimum is the closest thing to the true cost. Rounds also swap which precision goes first, so a phone ramping its clocks does not favour one of them.
  • The control is the point. It times highp against highp — the same program, twice — so its ratio is 1.00× by construction and anything it reads instead is pure noise. A workload has to beat that margin before the verdict calls it real.
  • Timing is performance.now() around each pass. EXT_disjoint_timer_query would be cleaner but almost no mobile browser exposes it; the device strip says whether yours does.
  • Speed is only half the question. Whether a given shader still looks right in fp16 is what the minifier's half-precision emulation checks offline, shader by shader.
